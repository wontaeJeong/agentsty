# Production Quality Gate

## 1. 적용 범위

새 기능과 Production 릴리스에 적용하는 공식 완료 기준이다. 정책/문서만 바꾸는 작업은 문서 정합성 및 기존 동작 회귀를 검증하며, 구현하지 않은 기능의 출시 승인을 의미하지 않는다. `make test`와 `make kind-test`는 필요한 회귀 기준이지 충분한 Production 인증이 아니다.

현재 저장소가 아래 모든 기준을 충족했다는 증거는 없다. 릴리스별 증거 검토 전에는 Production Ready로 표시하지 않는다. 태그 발행이나 이미지 게시만으로 승인되지 않는다.

## 2. 필수 증거

| 기준 | 검증 및 완료 증거 |
| --- | --- |
| 실제 사용자 시나리오 | 지원하는 클라이언트·Agent Runtime·provider로 생성/사용/재접속/삭제 등 사용자 흐름을 실제 배포에서 검증한다. stub만 사용한 성공은 해당 경로 검증으로 한정한다. |
| 인증·인가·위협 모델 | 정상/거부/만료/철회, 타인·다른 테넌트 세션 접근, 권한 상승 및 비신뢰 코드 위협을 검증하고 잔여 위험을 기록한다. |
| Secret·격리 | upstream 키 누출 부정 테스트와 최소 RBAC, 네트워크/자원/데이터 격리를 실제 환경에서 확인한다. 가짜 RuntimeClass는 VM 격리 증거가 아니다. |
| 장애·복구 | 의존성 중단, 컴포넌트/노드 재시작, 부분 실패, 토큰 만료, cleanup 실패를 주입한다. 복구 시간·데이터 손실 목표와 측정 결과, 보장하지 않는 복구 범위를 기록한다. 영속 상태가 있으면 백업/복원도 검증한다. |
| 다중 사용자·세션 | 목표 동시 사용자/세션 부하에서 권한·데이터 분리, 자원 경합, 오류 전파와 공정한 자원 통제를 검증한다. |
| 테스트 자동화 | unit, handler, reconcile, terminal/CLI, 통합/E2E와 누출 부정 테스트를 실행한다. Mock/Fake/Stub의 목적과 실제 연동 증거를 구분한다. |
| 안정적 계약 | 지원 API/CRD/클라이언트 버전, 오류·타임아웃 의미, 호환성 테스트, 업그레이드/마이그레이션 및 롤백 결과를 제공한다. |
| 관측성 | 주요 성공/실패/지연/자원 신호, 감사 이벤트, secret redaction, 경보 전달 및 대응 가능성을 검증한다. 원시 터미널/모델 본문 수집은 기본 비활성화한다. |
| 확장성·유지보수 | 목표 규모에서 병목과 확장 한계를 측정한다. 요구 SLO를 충족하는 HA/확장 전략, 운영 비용 및 필요한 ADR을 검토한다. |
| 재현 가능한 배포 | 버전 고정 이미지/구성, Secret 참조, 배포 전제조건, 재설치·업그레이드/롤백을 대표 환경에서 재현한다. 개발용 인증/설정을 그대로 사용하지 않는다. |
| 공식 문서·운영 가이드 | 지원 범위/한계, 구성·사용 가이드, 장애 대응·복구·키 회전·용량·업그레이드 절차를 실제 동작과 대조한다. |
| 성능·자원 | 지연/처리량/오류율, 동시성, CPU/메모리/저장소·네트워크 예산의 목표·단위·측정 구간을 먼저 정하고 실제 결과로 충족 여부를 판정한다. |

## 3. 릴리스 증거 기록 양식

릴리스 또는 기능 PR에서 아래 내용을 기록하고 승인자가 검토한다. 숫자는 제품 요구와 운영 위험에 맞춰 정하며 이 문서에서 근거 없이 공통 수치를 만들지 않는다.

```text
대상 기능/릴리스·커밋:
요구사항 및 ADR 링크:
지원 사용자 시나리오·runtime/provider·API/CRD 버전:
실행 환경·구성·이미지 버전:
기준별 책임자 및 검토/승인자:
기준별 목표·허용치·단위·부하/측정 구간:
실행 명령/테스트·실측 결과·근거 링크:
실패·미실행·미검증 및 테스트 대역의 한계:
잔여 위험·대응·운영/복구 가이드:
판정(충족/미충족/비적용)과 승인 근거:
```

미실행·실패·기준 미정은 충족이 아니다. 비적용은 기능 범위와 위험에 따른 근거 및 검토자 승인이 필요하며 보안 불변 조건을 면제하지 않는다. 목표나 검증이 부족하면 개발 중/실험 범위로 명시하고 Production 완료를 주장하지 않는다.

## 4. 기존 테스트의 의미

[Test Plan](TEST_PLAN.md), [kind 가이드](KIND_TESTING.md), [CI/CD](CI_CD.md)가 현재 자동화 범위를 설명한다. `make test`의 opt-in E2E가 skip된 결과를 실제 E2E 통과로 세지 않는다. kind에서 stub가 성공해도 실제 provider나 사용자 업무 성공이 보장되지 않으며, `handler: runc`인 Kata plumbing은 실제 Kata 격리를 증명하지 않는다.
